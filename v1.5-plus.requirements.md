# Version 1.5+ Roadmap & Future Possibilities

## Overview

**Status:** Two tiers.

1. **Planned for v1.5 (maintainer-committed):** a small, well-understood slate of
   improvements identified by the **v1.4 pre-release quality audit** (June 2026) and
   deliberately deferred out of v1.4 to protect its stability. These are documented
   below with the full reasoning and the thinking they came from — see
   [Planned for v1.5](#planned-for-v15--deferred-from-the-v14-quality-audit).
2. **Everything else: user-driven only.** Beyond the audit slate, future versions
   only happen if users actively request specific features.

**Approach (unchanged for tier 2):**
- Evidence-based: "20+ users requested Prometheus metrics"
- Not speculative: Don't build features hoping users want them
- Organic: Let real usage patterns drive evolution
- Minimal: Each release solves one specific, validated need

## Planned for v1.5 — deferred from the v1.4 quality audit

### Where this list comes from (context & thinking)

Before tagging v1.4.0 we ran a **three-track adversarial quality audit** of the
library: (a) a concurrency bug-hunt that tried to break the lock-free core under
`-race` (it could not — no race, lost update, or double-delivery was constructible
against the default config); (b) an API-design review comparing the surface against
the Go ecosystem (channels, `errgroup`, asaskevich/EventBus, olebedev/emitter,
cskr/pubsub) and Go idiom; (c) a test-rigor/doc-consistency review checking that
every claim is proven by a committed test.

The audit's **correctness and honesty findings were all fixed in v1.4** (a stale
godoc contradiction on `SignalListenerErr`, phantom "worker pool" test names from
the deleted v1.3 design, two missing proof tests for the async error-join race
safety and the cross-goroutine happens-before guarantee, and the #1 idiomatic gap —
handle-based unsubscription — closed by `AddListenerWithCancel`/`AddOnceWithCancel`).

What remains below is the audit's **refinement tier**: items that are real but not
correctness defects, where rushing them into v1.4 days before the tag carried more
risk than value. The maintainer decision (June 2026) was: **ship v1.4 in its
verified state; land these in v1.5 with the same evidence discipline.** Each item
records what it is, why the audit flagged it, why it was deferred, and a design
sketch so the v1.5 implementer starts from the finished thinking rather than
re-deriving it.

---

### P1. `AddListenerCtx` — context-scoped auto-unsubscribe  `[additive]`

**What:** `AddListenerCtx(ctx, handler, key ...string)` registers a listener that is
**automatically removed when `ctx` is done**. Sketch: register via the existing
internal-key machinery, then `go func() { <-ctx.Done(); s.RemoveListener(k) }()`.

**Why (audit reasoning):** the most common real-world leak with long-lived signals is
a **request/connection/session-scoped subscriber that outlives its scope** — our own
docs carry a "Memory Leak with Listeners" troubleshooting entry for exactly this.
Today the caller must remember teardown (`RemoveListener(key)` or a `WithCancel`
canceller). With `AddListenerCtx`, the `ctx` the caller already carries *becomes*
the teardown trigger; there is nothing to remember. This composes with, not
replaces, `AddListenerWithCancel`: the canceller is for *manual* teardown, ctx-scoping
is for *lifetime-bound* teardown.

**Why deferred:** it spawns a goroutine per ctx-scoped listener; we want a deliberate
decision (and tests) on goroutine accounting and on `ctx == nil`/already-done
semantics, not a same-week addition to a frozen release.

**Acceptance:** removal fires exactly once on ctx-done; already-canceled ctx adds
nothing (or adds-and-immediately-removes — decide and document); no goroutine leak
after removal (goleak-style assertion); `-race` clean; 100% coverage.

### P2. `WaitFor(ctx) (T, error)` — await the next emission  `[additive]`

**What:** block until the next emission and return its payload, or return `ctx.Err()`
at the deadline. Builds directly on v1.4's `AddOnceWithCancel`:

```go
func WaitFor[T any](ctx context.Context, sig Signal[T]) (T, error) {
    ch := make(chan T, 1)
    cancel := sig.AddOnceWithCancel(func(_ context.Context, v T) { ch <- v })
    defer cancel() // wins the race ⇒ the one-shot never fires after we give up
    select {
    case v := <-ch:
        return v, nil
    case <-ctx.Done():
        var zero T
        return zero, ctx.Err()
    }
}
```

**Why (audit reasoning):** "await an event" is one of the most common needs an event
library serves (olebedev/emitter hands back a channel for exactly this); today every
caller hand-rolls the snippet above — and the *correct* version needs the
cancel-wins-the-race guarantee that only `AddOnceWithCancel` provides. The library
should own the subtle code once, tested, instead of every user rewriting it.

**Why deferred:** decide whether it is a method (interface break, again) or a
package-level generic function `signals.WaitFor(ctx, sig)` (no break — **recommended**).

**Acceptance:** payload delivered exactly once; ctx-expiry returns `ctx.Err()` and the
pending one-shot is provably removed; concurrent emit-vs-timeout race `-race`-proven.

---

### P3. Per-signal panic handler — `SignalOptions.PanicHandler`  `[breaking-ish]`

**What:** move panic reporting from the process-global `SetPanicHandler` to an
optional per-signal `SignalOptions.PanicHandler func(recovered any)`, falling back to
the global default when unset.

**Why (audit reasoning):** the global handler is the one remaining *design* smell the
API review flagged. Process-global mutable state set by a library has a documented
failure mode our own godoc admits: *"a library that sets it overrides its host
application's handler"* — last writer wins, silently. Two subsystems in one binary
cannot hold different panic policies, and an imported dependency can hijack the
application's observability. Per-signal handlers (with the global as fallback)
eliminate the interference while keeping the simple default.

**Why deferred:** threading a handler through `BaseSignal` touches the recovery path
on every async handler goroutine — the most safety-critical code in the library
(slot-release ordering, handler-that-panics containment). That deserves its own
test cycle, not a pre-tag patch. Semi-breaking: behavior of existing
`SetPanicHandler` users must be preserved exactly when the option is unset.

**Acceptance:** per-signal handler wins over global; unset = identical v1.4 behavior;
panic-in-handler containment and slot-release invariants (I13/I14) re-proven.

---

### P4. `TryEmit` naming — add a clearer alias, deprecate gradually  `[additive]`

**What:** introduce `EmitWait(ctx, T) error` (or `EmitSync`) as the primary name;
keep `TryEmit` as a documented alias for at least one minor release.

**Why (audit reasoning):** in Go, the `Try*` prefix connotes *non-blocking /
fail-fast* (`mutex.TryLock` returns immediately). Our `TryEmit` is the **blocking,
wait-for-completion, collect-errors** path — nearly the opposite connotation. The
API review called the name "weak" and noted the v1.3→v1.4 rename (`EmitAndWait` →
`TryEmit`) arguably moved *away* from clarity. One name also covers two contracts
(sync stops-at-first-error; async joins-all) — the docs carry that load today.

**Why deferred (and the honest counter-argument):** v1.4 already ships a breaking
`Emit` semantic change plus a nine-method interface extension; renaming the method
users are being migrated *onto* mid-release would compound migration confusion.
There is also a real cost to API churn for naming taste — if v1.4 adoption shows no
actual user confusion, **dropping this item entirely is a legitimate outcome**.
Collect evidence first.

**Acceptance (if done):** alias delegates 1:1; both names on the interface or the
alias as a concrete-type method (decide); deprecation note in godoc + RELEASENOTES.

### P5. Listener ordering vs `RemoveListener` — SHIPPED IN v1.4 ✅

**Resolved in v1.4** (this item was pulled forward from the deferred slate). Removal is
now **order-preserving** (a fresh slice omitting the matched listener, not swap-remove),
so a `SyncSignal`'s emission order is **stable across add/remove**. On top of that,
`SignalOptions.Order` selects **FIFO** (default) or **LIFO** (reverse — the handler-stack /
reverse-teardown discipline). The order-preserving filter copies n-1 elements — the same
O(n) the whole-slice copy already pays — so it is effectively free, and the churn
microbenchmark did not regress. FR-9 / I15 restated; `doc.go`, RELEASENOTES, and the
pattern catalog updated; ordering property tests (FIFO + LIFO stable across a middle
removal) committed.

---

### P6. Doc tightenings carried from the audit  `[docs only]`

Three places the audit judged the current docs *accurate but undersold*:

1. **Bounded reentrancy deadlock is absolute at `MaxConcurrent=1`.** A listener on a
   bounded signal that re-emits via `TryEmit` with a non-cancellable ctx is a hard,
   unrecoverable deadlock — sizing does not save you at limit 1, and a cancellable
   ctx is the *only* liveness escape. Current docs imply sizing helps more than it
   does. Tighten `SignalOptions.MaxConcurrent` godoc + `doc.go` reentrancy bullet.
2. **Bounded fire-and-forget `Emit` can pin a dispatcher goroutine indefinitely** if
   a listener blocks forever holding the last slot (parked dispatcher is invisible
   to the caller). Recommend deadline-bearing contexts for any bounded signal.
3. **`OnError` sinks hold a concurrency slot** while they run on the handler
   goroutine of a bounded signal — a blocking sink starves the bound exactly like a
   blocking listener. Stated today; deserves a worked example in the patterns
   catalog (async-error-routing page).

---

### Explicitly considered and rejected by the audit (do not revive without new evidence)

- **`RemoveListenerAt(i)` / positional removal** — rejected in v1.4 (see
  requirements FR-5): position is not a stable identity under swap-remove +
  copy-on-write + concurrency; the `Add*` int return is a count, not an index.
- **8-method `WithCancel × WithErr` matrix** (`AddOnceWithErrAndCancel`, …) —
  rejected: `WithCancel` changes the return type, not the handler semantics; full
  orthogonality doubles the surface for a case keys already serve.
- **Worker pool / ring buffer (disruptor) async core** — rejected: a persistent pool
  buys throughput at the cost of lifecycle (`Close()`), and the disruptor shape fits
  one hot stream, not dynamic multi-subscriber fan-out. v1.4's goroutine-per-listener
  + optional semaphore is the right default for the library's scope; revisit only
  with evidence of real high-frequency async workloads hitting the wall.

### 3. Testing Utilities
**Priority:** MEDIUM
**Status:** Planned

Tools to make testing signal-based code easier.

**Requirements:**

#### Mock Signal
```go
// For testing
mock := signals.NewMock[Event](t)

// Use in code under test
processEvents(mock)

// Assertions
mock.AssertEmitted(t, 3)  // Assert 3 emissions
mock.AssertEmittedWith(t, func(e Event) bool {
    return e.Type == "expected"
})
mock.AssertNotEmitted(t)
```

#### Signal Recorder
```go
// Record all emissions for later inspection
recorder := signals.NewRecorder[Event]()
sig.AddListener(recorder.Record, "recorder")

// ... run code ...

// Inspect recorded events
events := recorder.Events()
assert.Len(t, events, 3)
assert.Equal(t, "user-login", events[0].Type)

// Replay in tests
for _, event := range events {
    testSig.Emit(ctx, event)
}
```

#### Signal Spy
```go
// Count calls without side effects
spy := signals.NewSpy[Event]()
sig.AddListener(spy.Listener(), "spy")

// Check later
assert.Equal(t, 5, spy.CallCount())
assert.True(t, spy.WasCalled())
```

**Success Criteria:**
- Works with standard `testing` package
- Compatible with testify assertions
- Minimal, focused API
- Well-documented examples

## Non-Functional Requirements

### Performance

- **Metrics overhead**: <1% CPU when enabled, zero when disabled
- **Memory overhead**: <5MB for metrics storage (histograms, counters)
- **Thread-safe**: All metrics operations concurrent-safe
- **No allocations**: Hot path (Stats() read) should minimize allocations

### Compatibility

- **Backward compatible**: 100% with v1.4
- **Opt-in**: All metrics disabled by default
- **No dependencies**: Core library stays dependency-free
- **Optional packages**: Prometheus exporter is separate module

### Testing

- **Test coverage**: >95% for all new code
- **Race detector**: 100% pass
- **Real-world validation**: Test with actual production patterns
- **Benchmarks**: Measure overhead of metrics collection

## Out of Scope for v1.5

### Explicitly Not Included

- ❌ **Auto-scaling worker pools** - Complex, not production-validated need
- ❌ **Time-series storage** - Use Prometheus/Grafana
- ❌ **Built-in profiling** - Use Go's pprof
- ❌ **Distributed tracing** - Use OpenTelemetry if needed
- ❌ **Advanced aggregation** - Keep it simple
- ❌ **Real-time dashboards** - Use Grafana

### Rationale

v1.5 provides the **data** (metrics, testing tools), but relies on external tools for **analysis** (Prometheus, Grafana, standard testing frameworks). This keeps the library focused and maintainable.

## Decision Criteria for Future Releases

**Before building ANY future version, require:**

1. **User demand**: 10+ users request the same feature via issues/discussions
2. **Can't DIY**: Users can't easily solve it themselves
3. **In scope**: Feature fits in-process signaling (no enterprise theater)
4. **Maintainable**: Won't create maintenance burden
5. **Evidence**: Real production use cases, not speculation

**Examples of what WOULD trigger a release:**
- "15 users asked for Prometheus metrics" → Consider metrics package
- "Multiple bug reports about testing difficulties" → Consider test utilities
- "Common pattern in 20+ codebases" → Consider adding pattern to library

**Examples of what would NOT trigger a release:**
- "Might be useful someday" → No
- "Enterprise feature checklist" → No
- "Competing library has it" → Not enough reason
- "Only 2 users mentioned it" → Too few
